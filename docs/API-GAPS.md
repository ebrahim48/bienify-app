# Backend gaps the app works around

Endpoints the app needs and the server does not serve, found by wiring the
screens to it. Each one is handled in the app rather than faked, and each is a
small backend change away from being handled properly.

`docs/LIVE-API-CHECK.md` is regenerated by the live suite on every run, so
these live here instead.

## A doctor cannot list the orders they requested

`GET /api/v1/lab-orders` filters on `patientId === req.user.id`, so it answers
"the orders I am the subject of". A doctor can *create* an order —
`requestedByDoctorId` is stamped on it — and *review* one by id, but no route
answers "the orders I requested".

**Where it shows:** the practitioner's **Results to Review** screen. Its
Patients segment is built from the appointment list; its Lab and Radiology
segments still render `DoctorOrdersData`.

**Fix:** a `role=doctor` filter on that endpoint, matching the one
`GET /appointments` already has.

## A shop cannot see who placed an order

`GET /api/v1/pharmacies/me/orders` does not populate `patientId`, so the order
carries an id and no name, phone or address for the customer.

**Where it shows:** every row of the shop's order book. The card falls back to
the order code (`ORD-B6F4`) rather than printing the same placeholder name on
all of them.

**Fix:** `.populate('patientId', 'profile.name phone')` on that query, as
`listAppointments` already does.

## A shop cannot see its own delisted stock

`GET /api/v1/medicines` hard-filters `isActive: true`. That is right for the
customer's catalogue, but it is also the only list of a shop's medicines — so
a product taken off sale disappears from the owner's shelf and cannot be put
back from the app.

**Where it shows:** the Medicines tab. Switching a row off removes it from the
list, and the owner is told so, because a row that silently vanishes reads as
a bug.

**Fix:** an owner-scoped `GET /pharmacies/me/medicines` that returns both, or
an `includeInactive` flag honoured only for the owning shop.
