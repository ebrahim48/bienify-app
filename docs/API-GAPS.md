# Backend gaps the app works around

Endpoints the app needs and the server does not serve, found by wiring the
screens to it. Each one is handled in the app rather than faked, and each is a
small backend change away from being handled properly.

`docs/LIVE-API-CHECK.md` is regenerated by the live suite on every run, so
these live here instead.

## A doctor cannot list the orders they requested

`GET /api/v1/lab-orders` filters on `patientId === req.user.id`, so it answers
"the orders I am the subject of". A doctor can *create* an order —
`requestedByDoctorId` is stamped on it — and *review* one by id, but no route
answers "the orders I requested".

**Where it shows:** the practitioner's **Results to Review** screen. Its
Patients segment is built from the appointment list; its Lab and Radiology
segments still render `DoctorOrdersData`.

**Fix:** a `role=doctor` filter on that endpoint, matching the one
`GET /appointments` already has.

## A shop cannot see who placed an order

`GET /api/v1/pharmacies/me/orders` does not populate `patientId`, so the order
carries an id and no name, phone or address for the customer.

**Where it shows:** every row of the shop's order book. The card falls back to
the order code (`ORD-B6F4`) rather than printing the same placeholder name on
all of them.

**Fix:** `.populate('patientId', 'profile.name phone')` on that query, as
`listAppointments` already does.

## A shop cannot see its own delisted stock

`GET /api/v1/medicines` hard-filters `isActive: true`. That is right for the
customer's catalogue, but it is also the only list of a shop's medicines — so
a product taken off sale disappears from the owner's shelf and cannot be put
back from the app.

**Where it shows:** the Medicines tab. Switching a row off removes it from the
list, and the owner is told so, because a row that silently vanishes reads as
a bug.

**Fix:** an owner-scoped `GET /pharmacies/me/medicines` that returns both, or
an `includeInactive` flag honoured only for the owning shop.

## A delivery job carries almost nothing the courier needs

A delivery document holds an order id, two addresses and a status. It holds no
fee, no line items and no distance — and neither `GET /deliveries/available`
nor `GET /riders/me/deliveries` populates its references, so there is no
customer name either.

**Where it shows:** every job card on the courier's board. The fee, the items
and the distance come back empty and the card drops them; the pickup and
dropoff addresses are the only real content on it.

**Fix:** populate `patientId` and `orderId` on both lists, and carry a
`feeMinor` on the delivery — the courier's pay is decided when the job is
created, not when it is claimed.

## The courier has no rating

`IRiderProfile` keeps no rating, and `POST /reviews` accepts `subjectKind:
'rider'` but nothing reads it back onto the profile. The dashboard prints a
dash where the design has a score.

**Fix:** the same `rating: { average, count }` shape the doctor profile
already carries.

## `requiresPrescription=false` returns exactly what it excludes

`listMedicinesQuerySchema` coerces that filter with `z.coerce.boolean()`, and
in JavaScript `Boolean("false")` is `true` — so the query string `false`
becomes the filter `true`. `inStockOnly=false` has the same fault.

**Where it shows:** nowhere in the app, which narrows those lists client-side.
`test/live/live_rider_test.dart` does the same, and says why.

**Fix:** a string-to-boolean preprocessor on both flags, e.g.
`z.preprocess((v) => v === 'true' || v === true, z.boolean())`.

## A payment point has no coordinates and no kind

`IPaymentPoint` keeps a name, an address, a city, a phone and opening hours.
The Nearby Payment Points screen draws a map with a pin per point and a
distance on every row, and neither is derivable from that.

**Where it shows:** every point maps to the `agent` icon, the distance column
prints the city instead, and the map has nothing to place a pin at.

**Fix:** `location: { lat, lng }` on the point, a `kind` enum matching the
five the design draws, and a `near=lat,lng` query so the server can sort by
distance rather than the app doing it with no coordinates to work from.

## A patient has no lifetime spend

`GET /wallet` returns a balance and nothing else, so My Wallet's "Total spent"
and "Added this month" have no field behind them.

**Where it shows:** both are summed from the transaction page the screen is
already showing — which is right as far as that page goes, and wrong for a
patient with more than 100 movements.

**Fix:** the same shape `GET /wallet/earnings` gives a provider — a couple of
aggregate totals on the patient's wallet.
